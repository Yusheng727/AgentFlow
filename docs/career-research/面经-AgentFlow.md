## 1. 项目简介（简历可用，1-2 句）

> AgentFlow 是我从 0 用 Java 21 实现的 Multi-Agent 编排引擎：YAML 声明工作流，BSP 执行模型驱动，两级 Checkpoint 崩溃恢复防止 LLM 重复计费，扩展动态路由、迭代循环、Kafka 异步解耦、人工审批（HITL）与列级静态加密；13 个 Maven 模块、500+ 测试、JaCoCo 80% 门禁、CI 全绿，真实 PostgreSQL / Kafka / DeepSeek 三环境端到端验证。

## 2. 简历 bullet（5 条 · 通用支柱名）

- **分层并行编排：** 静态 DAG 场景下原生的线程池 + 锁方案并发模型复杂、合并结果不确定。我实现 BSP（整体同步并行）执行引擎：同层节点虚拟线程并行、层间栅栏确定性合并、并发写按声明序归并，免锁达成确定性可测的并发；并扩展运行时条件路由与有界循环而不破坏同步不变量，路由决策落检查点供恢复重放。结果：静态/路由/循环三层测试全绿，279+310 引擎级断言锁语义。
- **分层容错与状态恢复：** LLM 节点执行是真金白银，崩溃后整层重跑意味着重复计费。我实现两级检查点（节点级完成即写 + 层级栅栏快照）与崩溃恢复协议，恢复时只重跑崩溃层未完成节点、已完成节点重放输出；多视角评审修复了恢复层定位偏移与孤立完成记录防护两个正确性缺陷。结果：真 PostgreSQL 集成测试实跑验证恢复三不变量（不丢进度、不重复计费、不用脏数据）。
- **请求可靠性治理（异步解耦与幂等）：** 长任务同步执行会拖垮提交入口，且消息重复投递会重复执行。我将提交与执行经消息队列解耦，消费端以单条条件更新原子认领执行权，在至少一次投递语义下防止重复消费双跑双计费；配合提交守卫事前拦截失控任务、预算逐轮记账事后告警两道成本防线。过程中修复了重试被幂等防护吞掉静默失效的真缺陷——本地测试全绿、真实队列模式才暴露，成为「测试绿不等于生产生效」的直接证据。
- **人机协同与框架可移植性：** 自动化工作流缺少敏感操作的人工确认环节。我实现「中断→人工决策→恢复」全链路：上下文快照随审批单落库（只含兄弟节点输出防恢复双跑），审批后重跑待批节点续跑下游，审批身份由服务端推导防伪造、决策原子幂等；同时把两类主流 LLM 框架收敛到同一窄接口——核心模块零框架依赖可构建级验证，检索增强生成作为扩展点接入且引擎零改动。结果：含 Web 审批中心的完整闭环；真实 DeepSeek 端到端验证通过。
- **质量与安全工程：** 个人项目常见质量与安全缺位。我建立 500+ 测试 / 覆盖率 80% 门禁 / CI 全绿的质量底座；安全上实现工具级授权（配置∪数据库、管理员管理、防自授特权工具）与 5 处敏感列 AES-256-GCM 静态加密，生产环境缺密钥即拒绝启动（fail-closed），API 密钥只存哈希、所有权校验防越权。结果：真实 PG 密文证据 + 装配级 fail-closed 测试锁定。

> 口径提醒：每条的结果都用「测试全绿/实跑验证」这类**可验证事实**，不编造性能数字。个人职责边界 = AI 辅助开发、本人负责架构决策与质量把关（被问 AI 使用时的标准话术见 08 §〇）。

## 3. 面试问题（18 主问题 × 追问，按频率分组）

### 主题 A：执行模型与并发（后端必考）

**A1（主问）「介绍一下这个项目的核心并发模型，为什么这么设计？」**

口播：这个项目的核心是一套 BSP——整体同步并行——执行引擎。它的形态是把工作流按依赖关系预分层，同一层内的节点用 Java 21 虚拟线程并行执行，彼此完全隔离；一层全部执行完后有一个栅栏点做确定性合并，然后才进入下一层。我当时面对的问题是：多 Agent 并发执行时，节点之间写共享上下文会产生竞态，用锁能保证正确但合并结果依赖完成时序、不可复现。我选 BSP 的理由是靠结构而不是靠锁来消除竞态——层内节点读的是不可变快照、互相看不见写入，全局写只在栅栏后的单线程段按声明顺序归并，所以并发正确性和结果确定性是结构保证的。代价是并行度受层内宽度限制，但工作流编排是几十个节点的有界场景，这个取舍是合适的。最终引擎层三百多个测试全绿，并发写冲突从未出现过一例。

- 追问1「CompletableFuture 栅栏具体怎么做的？虚拟线程在这里解决了什么？」口播：栅栏的实现就是收集这一层所有节点的执行句柄，用一个 allOf 阻塞等待全部完成后才继续，任何一个失败则集中走异常处理。虚拟线程在这里解决的是阻塞成本问题：每个节点背后是一次 LLM 调用，秒级的阻塞非常常见，如果用传统平台线程池，几十个并发节点就把线程打满、后续任务全在排队；虚拟线程阻塞时自动让出底层载体线程去跑别的任务，几十上百个并发节点的调度开销可以忽略。我认为这和线程池方案的本质差异是：线程池方案里线程是稀缺资源要精心管理池子大小，虚拟线程把「一个任务一个线程」变回了默认，代码不用再为并发度做池化调参——这也是 Java 21 选型对引擎的直接收益。
- 追问2「如果某个节点一直不返回怎么办？」口播：我做了三层防护。第一层是节点级超时：每个节点的执行句柄带超时等待，超时直接中断对应的虚拟线程，中断信号会传播到阻塞中的 LLM 调用；第二层是异常分类：超时算临时性异常会进重试逻辑，重试耗尽才升级为失败传播；第三层是工作流总超时兜底，防止重试叠加把单节点超时放大成整体无界等待，总超时触发中止前还会执行错误处理器做上下文补偿。另外有一个我踩过的隐蔽点值得主动说：超时中止后，还在飞的任务可能事后把完成记录写进数据库，恢复时必须按工作流状态鉴别这种孤立的完成记录——宁可这一层整体重跑，也不能把没过栅栏的脏数据当有效进度。

**A2（主问）「多个节点同时写一个输出通道怎么处理冲突？」**

口播：我在需求分析阶段就把它定为必须确定性解决的问题。机制是声明序归并器：每个输出通道在 YAML 里声明归并策略，比如覆盖、拼接、取最大值；当同层多个节点写同一通道时，栅栏后按 YAML 里的声明顺序依次套用策略合并。关键点是「声明序」而不是「完成序」——完成时序受调度影响不可复现，声明序是静态的、跑一百次结果一样。这个设计让上层用户对冲突有预期控制权：要么显式声明策略，要么解析期直接拒绝多写一读的歧义拓扑。测试里我专门锁了「同层并发写合并结果确定」这个性质。

- 追问1「为什么不做成先到先得或者时间戳最新优先？」口播：因为这两种方案都把不确定性引入了结果。先到先得的「先」取决于线程调度，调度受机器负载影响，同一份输入两次执行可能留下不同的赢家；时间戳最新优先则依赖时钟的单调性和精度，我在真 PostgreSQL 集成测试里实际踩过这个问题——快速连续写入时毫秒级时间戳发生碰撞，按时间倒序排列的结果顺序不确定，最后只能在测试里显式错开时间戳来消除抖动。这两件事让我把原则定死：结果确定性是这个项目的第一哲学，任何依赖时序或时钟的合并方案都被排除，最终一切以静态的声明顺序为准。
- 追问2「层和层之间的数据怎么传递？」口播：传递机制是「栅栏合并后的上下文成为下一层的输入视图」：上层节点执行完，各自输出在栅栏处归并进工作流上下文，下层节点启动时拿到的是这个合并后的只读快照，通过占位符按通道名引用上游的输出。整个数据流是单向按层推进的——只允许引用更早层的输出，不存在跨层直写、也不存在同层互读，这两条约束让数据依赖和分层结果天然一致。工程上的好处是：数据流问题在解析期就能定位——引用了不存在的通道或者构成了环，校验直接报错，不用等运行时才发现。

### 主题 B：容错与崩溃恢复（后端必考）

**B1（主问）「引擎执行到一半崩溃了怎么办？怎么保证不重复计费？」**

口播：这是这个项目最重的工程点。LLM 调用是真金白银，崩溃恢复最怕两件事：丢进度，或者重复执行导致重复花钱。我的方案是两级检查点：节点级——每个节点一执行完，立刻把输出同步写入 PostgreSQL，这是钱的问题不能异步；层级——每层栅栏处写一个快照，标记这层整体完成。恢复协议先定位崩溃发生在哪一层，然后只重跑该层还没有完成记录的节点，之前所有层的输出直接从库里重放，绝不重新调用 LLM——这就是防重复计费的核心。这个恢复协议本身还修过两个评审抓出来的正确性缺陷：一个是恢复时查错了层，本该查崩溃层本身却查了已完成的层；另一个是超时中断后残留在飞任务的完成记录会污染恢复判断，我加了按工作流状态鉴别的防护。这两件事让我对「正确性 bug 在测试环境藏得住」有了切身体会，因为两个都是真库集成测试和多人评审才暴露的。

- 追问1「为什么节点完成要同步写？异步批量不是性能更好吗？」口播：我认真权衡过这个方案。异步批量写确实吞吐更高，但它在崩溃窗口内有丢失风险——节点实际执行完了、LLM 的钱已经花了，但完成记录还在内存缓冲里没落库，这时进程崩了，恢复时就会认为这个节点没执行过，重新调用一次 LLM，等于重复计费。同步写在完成的那一刻就持久化了，钱和记录永远一致；它带来的写库压力我用信号量限流控制——最多二十个并发写库，超出的排队等待，性能损失可控。我的取舍原则是：防重复计费是钱的硬约束，写库性能是体验的软约束，硬约束优先。而且这个决策有验证——真 PostgreSQL 集成测试覆盖了完成即写的往返。
- 追问2「恢复这个操作谁来触发？」口播：如实回答：恢复协议本身已经实现并且验证过——恢复的每一步都有测试，包括查层定位、已完成节点重放、孤立记录防护，还在真 PostgreSQL 上跑过集成验证。但生产侧「怎么发现进程崩了、谁来调恢复」这层调度编排没有做，目前恢复协议的调用方全部是测试代码。这是个人项目的已知边界，我主动说边界比被面试官戳穿要可信得多。如果生产化，我的思路是部署侧加进程健康检测加恢复触发，或者消费端在认领执行权时检测到残留的执行中状态就先走恢复流程，这两个方向我都想过。

**B2（主问）「重试策略是怎么设计的？什么情况该重试什么情况不该？」**

口播：我把重试分成三个层次回答。第一是分类前置：异常先分类，只有临时性异常——网络抖动、超时、限流——才值得重试，逻辑错误、参数错误重试多少次都没用，只会放大成本。第二是预算封顶：单节点最多三次重试、每次内部还有输出格式校验的重试、两者组合有九次上限——不封顶的话格式校验循环叠加网络重试会指数放大。第三是记账随行：重试的每一轮都计入成本预算，包括失败的轮次——这里我踩过一个真坑，最初的记账只记成功路径的最后一次调用，中间轮次全漏了，实测成本低估最多三倍，是评审抓出来后改成逐轮记账的。所以我对重试的理解是：难点不在循环本身，在于何时停和算多少钱。

- 追问1「重试会不会导致上游重复执行？」口播：不会，重试的边界被严格限定在单个节点内部。重试发生在该节点自己的执行过程中——调用失败、退避、再调用，都是同一个执行句柄里的事，只有所有重试机会耗尽、异常升级为致命类型，失败才向工作流传播，触发的是整条工作流的失败中止而不是任何形式的重放。上游节点更不受影响：它们的输出早就持久化了，后续任何恢复场景都是直接重放这条输出。所以「重试」和「恢复」在我这是两个正交机制：前者是节点内的执行策略，后者是工作流级的进度保护，互不越界。
- 追问2「指数退避怎么实现的？」口播：基础实现就是每次重试间隔按固定倍率增长，让下游有喘息时间。实现过程中抓到一个精度细节：倍率计算用浮点乘法会产出小数间隔，比如一点五倍乘出二点四秒，而我的调度粒度是整数，直接截断会系统性偏短，退避效果打折——所以做了向下取整并明确了精度语义。这个细节本身很小，但它给我的启示是：凡是从设计文档落到代码的参数计算，都要想一遍精度和边界值，否则测试全绿也只是在验证错误语义的正确实现。这类「参数为什么是这个值」的问题我都能给出出处。

### 主题 C：分布式解耦与幂等（后端必考）

**C1（主问）「为什么要引入 Kafka？整个提交到执行的链路讲一下。」**

口播：最初版本提交和执行在一个进程里，REST 收到提交后起异步任务直接执行。问题是：执行入口和业务入口耦合在一起，服务重启在途任务就悬空了，未来跨节点部署也没有路径。所以我把提交和执行经 Kafka 解耦——提交接口只做校验、落库置待执行状态、往主题发一条消息就返回；消费者拉取消息后认领执行权、真正跑引擎。这条链路上我最看重的是幂等设计：Kafka 是至少一次投递，消息可能重复送，我的消费者用一条带状态条件的更新原子认领执行权——状态从待执行改到执行中，两个消费者抢同一条消息只有一个能改成功，另一个影响行数为零就放弃，所以重复投递不会导致重复执行重复计费。这个幂等是做在业务状态机的条件转移上的，不是依赖什么消费框架注解，所以对本地派发、消息队列、未来任何派发方式统一生效。

- 追问1「新上线的消费者会不会漏掉订阅之前的消息？」口播：不会，消费端的起始偏移我显式配置为 earliest——也就是新消费组第一次订阅时，从分区里最早的未过期消息开始拉取。选它是因为这是任务队列语义：提交进来的工作流就是待办任务，新扩容的消费者必须能看到队列里积压的任务，而不是只处理自己上线之后的新消息，否则就会出现「任务在队列里躺着没人认领」的静默丢失。选 earliest 通常有重复消费的顾虑，但正因为我的消费端做了状态机幂等——已认领的消息重扫一次也只是空跑一次认领、不会重复执行——所以重扫旧消息是安全的， earliest 的风险已经被幂等消化掉了。这两个配置是配套决策，不是独立拍的。
- 追问2「现在是分布式部署吗？」口播：如实回答：目前生产者和消费者在同一个应用进程里，Kafka 解耦的是「提交入口」和「执行引擎」这两个模块的边界，还不是物理节点的分布式。发送侧也还没做本地消息表这类事务性发件箱，发送失败会留下一条悬空的待执行记录，这是我明确记录的已知边界。但我想说清楚这一步买到的是什么：消费者的幂等认领、终态跳过、偏移语义这些，全部是按多实例扩展预留的语义，将来部署成多节点，应用代码不需要为水平扩展重写，加部署就行。真 Kafka 的端到端测试也验证过重复投递不重跑、连续双工作流这些场景。知道现在是半程、并说清后半程怎么走，比含糊其辞说「分布式」更专业。

**C2（主问）「讲一个你印象最深的 bug——最好是测试全绿但生产场景才暴露的。」**

口播：我有一个教科书级的案例。重试接口在引入 Kafka 派发后失效了：本地模式一切正常，切到 Kafka 模式后重试请求发出去了、但工作流永远不会重新执行。排查下来是幂等防护和重试语义的冲突——消费者的幂等逻辑是「已是终态的消息直接跳过」，这本来是防重复消费的，但重试恰恰是要重新执行一个已终态的工作流，于是被幂等「正确地」吞掉了，静默失效。本地直跑模式不走消费者，所以单测全绿；只有真 Kafka 的端到端测试才暴露。修复是让重试先显式把状态复位回待执行再派发。这个 bug 给我三个教训：幂等防护要区分「重复的正常消息」和「刻意的重试意图」；涉及中间件语义的路径必须有真依赖的集成测试；测试绿不等于生产生效——这句话我现在面试时经常主动拿来讲。

- 追问1「怎么在测试层面防止这类问题再发生？」口播：我做了三层固化。第一层，把「消息队列模式下重试会真正重新执行」写成端到端断言——用真消息中间件跑：发一条重试消息，断言工作流从失败状态真正重新执行到终态；这类测试在无中间件的环境自动跳过，本地不红，但持续集成有真环境时会跑。第二层，给消费端语义本身补了不依赖中间件的兼容冒烟测试——消息上下文能起、各种字段类型能正确往返，把消费逻辑与序列化语义从集成环境里剥离出来先测。第三层是流程性的：每发现一个「测试没覆盖到生产语义」的缺口，就把那个语义固化成断言，而不是只修掉当次的问题。我认为回归测试的价值就在这——让每个吃过的亏都变成一道永久闸门。
- 追问2「这个幂等在高并发下可靠吗？」口播：可靠，可靠性来自数据库的保证而不是我的代码自觉。单条带条件的更新语句在数据库层是原子的：两个事务同时执行同一条认领语句时，行锁保证它们串行执行，第一个事务把状态从待执行改成执行中并提交；第二个事务随后执行，它的条件「状态等于待执行」已经匹配不到这一行，影响行数为零，于是放弃执行——不存在两个都成功的窗口。我还专门写了并发测试验证「恰好一个胜出」：多线程同时认领同一条记录，断言恰好一个成功、其余全部空手而归，且执行结果只跑了一次。另外从扩展性讲，这个方案的并发上限就是数据库单行更新的能力，认领动作本身极轻，真正的重活是认领之后的工作流执行，所以这里不是瓶颈所在。

### 主题 D：人机协同 HITL（Agent 岗重点）

**D1（主问）「人工审批是怎么实现的？从暂停到恢复完整讲一遍。」**

口播：完整链路五步。第一步，工作流执行到声明了需要审批的节点时，该节点抛出审批请求信号；第二步，引擎在当层栅栏处识别这个信号，暂停整个工作流——注意不是走异常路径，我特意用暂停标志穿透执行循环，因为异常控制流会被重试和兜底逻辑误伤；第三步，把当前上下文做快照，连同审批单一起落库，工作流状态置为等待审批，快照里只包含同层兄弟节点的输出、不包含待批节点自己；第四步，审批人通过 REST 接口或网页审批中心做批准或驳回，审批身份由服务端从调用方密钥推导，客户端传什么都不认——防身份伪造，审批动作是条件更新、两个人同时批同一单只有一个生效；第五步，批准则重建上下文、只重跑那个待批节点并注入决策结果，然后从审批层继续往下跑完，驳回则直接置失败终态。支持多级审批链——恢复后待批节点可以再次触发审批再暂停。

- 追问1「快照为什么只存兄弟节点的输出？」口播：这个设计的出发点还是防重复计费，只是换了个场景。审批恢复时，同层兄弟节点不应该重跑——它们已经执行完成、LLM 的调用费已经真实发生了，重跑就是纯浪费；但待批节点本身没有被批准过、还没执行，所以它必须在恢复时重新执行并注入审批决策。如果快照存了全部上下文、恢复时整体重放，兄弟节点就会被无谓地再调一次 LLM。所以我让暂停时的快照只包含兄弟输出、明确排除待批节点，恢复时兄弟直接复用快照、待批节点单独重跑——崩溃恢复防的是「重跑已完成的节点」，审批恢复防的是「重跑兄弟节点」，同一个「已花的钱不花第二次」的原则在两个场景的镜像。
- 追问2「审批单持久化失败怎么办？」口播：我把它定义为致命错误、直接让工作流失败，不做任何静默降级。理由是语义层面的：暂停这个状态的全部意义就是「可恢复」——工作流停下来等着外部输入；如果审批单没写成功库、快照也没落盘，那这次暂停就永远没有恢复的凭据了，工作流实际上卡死在一个没有任何人能推动的状态。与其假装暂停成功、留一个僵尸状态，不如立刻失败、让用户重新提交。这条和我在用户界面上「写操作不做降级兜底」是同一条纪律：假成功比显式失败危险得多，因为用户基于假状态做的后续决策全错。
- 追问3「审批会不会阻塞太久拖垮系统？」口播：不会拖垮，因为等待审批的工作流不占用任何执行资源。暂停的实质是把工作流状态持久化到数据库——状态、快照、审批单都是表记录，不持有任何线程、连接或内存结构，一百个等待审批的工作流和零个的系统负载是一样的，恢复时从库里读出来重建现场继续跑。这是持久化暂停相对内存暂停的根本优势。目前没有做审批超时的自动批准或自动驳回，这是已知边界；业务上需要的话，加一个定时任务扫描超时的等待审批记录、按配置默认决策即可，架构上不需要任何改动。

### 主题 E：可移植性与扩展性（Agent 岗重点）

**E1（主问）「你说支持多个 LLM 框架，怎么证明的？换个框架要改多少？」**

口播：我的证明方式不是画架构图，而是构建级验证。做法分三层：第一，定义一个只有两个方法的窄接口作为引擎和所有 Agent 实现的唯一契约；第二，两个主流框架各自写一个适配器实现这个接口，框架的全部知识——会话构建、异常翻译、token 统计——都关在适配器文件里；第三，也是最有说服力的，核心模块的构建配置里零 LLM 框架依赖，把任何一个适配器模块从构建里删掉，引擎照样编译通过。这两条约束合起来意味着：换框架、升框架版本，影响面收敛在单个适配器文件——两个框架升级时各自的兼容性坑我都是只在适配器里处理掉的。另外我还做了第三种实现来验证扩展点：检索增强生成作为一个新的 Agent 实现接入，有一个专门的测试直接用引擎跑它，引擎和 DSL 一行没改就通过——证明扩展靠契约成立，不靠对引擎内部的白盒改动。

- 追问1「两个框架的适配器实现有什么真实的坑？」口播：举两个最典型的。一个是响应对象的可变状态问题：那个框架的响应是个会自我消耗的结构，取文本内容和取 token 用量是两个方法，各自会触发一遍完整的处理链，第二次调用直接撞上已消费的内部状态抛错——看起来是两个普通的 getter，实际是一次性的。解法是只调用一次入口，文本和用量从同一个响应对象里取齐。另一个更隐蔽：框架自带的工具执行器把所有异常吞掉、把原始错误信息当字符串返回给模型，外面包多少层 try-catch 都拦不到——因为异常根本没抛出来。而工具的原始报错可能包含内部路径、堆栈信息，直接喂给模型有泄漏风险，我只能放弃它的执行器、自己实现一个安全的工具执行，把真实原因只写服务端日志、给模型返回泛化的错误信息。这两个坑都只有真读过框架源码才可能预判，也都被隔离在适配器单文件里，引擎毫发无伤。
- 追问2「RAG 为什么不做成引擎内置能力？」口播：因为 RAG 是 Agent 的内部实现细节，不是编排引擎的关注点。引擎的职责边界是「把任何实现了 Agent 契约的东西编排起来」——什么时候调、怎么并行、崩了怎么办，至于一个 Agent 内部是纯生成、还是先检索再生成，引擎既不关心也不应该关心。把 RAG 内置进引擎，等于把一种 Agent 的实现细节上升成了平台能力，每加一种模式引擎就要改一次，扩展点就名存实亡了。所以我用检索增强作为扩展点的实证：写一个带检索能力的新 Agent 实现，注册进引擎直接跑，有一个专门的测试断言「引擎与 DSL 零改动」这个架构性质本身。我的检索实现是有意的最小验证——内存向量库加确定性的词袋向量化，目的是证明契约成立，不是做产品级检索，这个定位我会主动说清。

### 主题 F：安全与质量（收尾防线）

**F1（主问）「这个系统的安全做了哪些层？」**

口播：我按纵深防御组织，每层对应一个具体攻击场景。第一层认证：接口密钥访问，数据库只存哈希，拖库也拿不到可用凭证。第二层所有权校验：用户 A 拿着 ID 访问用户 B 的工作流会被拒绝，防水平越权。第三层工具授权：工作流能引用哪些工具是按调用方白名单控制的，白名单来自配置和数据库两处求和，管理接口只有管理员密钥能操作，防止普通用户给自己授特权工具。第四层提交守卫：提交时校验节点数和预估成本上限，超了直接拒绝，防止恶意或失控的工作流起无界并发烧钱。第五层静态加密：五处含业务敏感数据的列用带认证的加密算法加密落库，密文带自描述前缀兼容旧明文数据，生产环境启动时缺密钥直接拒绝启动——把「忘了配密钥」从静默明文落库变成必须处理的启动失败。另外凭证只从环境变量读、提示词和轨迹过脱敏。加密的选列我有一个明确判据：这一列里是否有业务敏感数据，按判据最小必要覆盖，不是拍脑袋全加密。

- 追问1「fail-closed 是什么意思，为什么生产要这样？」口播：fail-closed 就是失败即关闭——前提条件不满足时系统拒绝工作，而不是带着风险继续。具体到我的加密模块：生产装配模式下，启动时检测不到加密密钥就直接启动失败，而不是降级成明文落库。反面方案是 fail-open：没密钥就明文存，表面上服务还能跑，实际上静态加密这个安全机制等于不存在，而且没人会去看一条启动日志——风险被完全掩盖了。fail-closed 把「忘了配密钥」从静默的安全退化变成必须立刻处理的启动故障，问题在第一时间暴露。实现上我提供宽严两种装配方式：开发环境宽松——没密钥就走不加密，本地开发零配置；生产环境严格——缺密钥拒绝启动。同一个加密实现、两种装配姿势，开发体验和生产安全不互搏，这个宽严分离本身也是我认可的一个工程模式。
- 追问2「加密的密钥怎么管理？轮换呢？」口播：密钥管理当前的原则是「只从环境变量读」：不写配置文件、不落数据库、不进代码仓库，启动时读取，缺失按上一条说的拒绝启动。密文格式我设计成自描述的——每段密文带算法前缀标识，读库时按前缀识别走解密，没有前缀的旧明文行按兼容逻辑读，所以加密上线不影响存量数据。轮换确实没有做：换新密钥之后，旧密钥加密的存量行就解不开了，这是一个明确的已知边界。我为它做的缓解是消费端容错——聚合查询里单行解密失败只跳过该行并记警告日志，不让整个列表接口失败。轮换的正确做法也想过：密文里记录密钥版本、双密钥过渡期读旧写新、后台批量重加密，属于生产化清单里的一项。
- 追问3「覆盖率门禁怎么落地的？」口播：落在构建里，不是落在口号里。构建配置里强制每个有代码的模块指令级覆盖率不低于百分之八十，低于门禁则构建直接失败——所以它是一道硬门禁，任何一次提交想合进去，覆盖率不够就是过不去，不存在「先合了以后补测试」的空间。它还产生过一个正向的副作用：预算模块为了过门禁补测试，我写了并发场景下预算触发恰好一次的断言，结果这个断言反过来帮我验证了预算只触发一次的语义实现是对的。这让我对门禁的评价是：它不只是衡量测试多少的指标，更是逼着把关键语义固化成断言的机制。当然我也清楚覆盖率高不等于没缺陷，它保的是「已有行为不回归」，不保「行为本身正确」。

### 主题 G：诚实性压力测试（高频收尾）

**G1（主问）「这个项目是 AI 辅助开发的吧？哪些是你自己做的？」**

口播：主动承认：AI 辅助开发，代码大部分由 AI 生成，但架构决策和质量把关是我做的——技术选型、每一次方案取舍、每一轮多视角评审发现的缺陷判定与修复验证，都是我主导的，项目里有完整的评审记录和决策文档可查。我的观点是：AI 时代工程师的核心价值已经从「写每一行代码」转向「决定写什么、判断对不对、把控质量边界」，这个项目就是我这个工作方式的完整演练——500 多个测试、多轮评审修复记录、三个真实环境的端到端验证，这些是我作为负责人的产出。我不虚构「手写每一行」，但每个设计为什么这么做我可以讲到取舍级别。有些 JD 明确把 AI 辅助开发工具的经验列为加分项，我是把它当能力展示而不是遮掩的事。

- 追问1「那面试里我怎么验证你的真实水平？」口播：我认为最有效的验证就是眼下这样的追问——您可以对我讲的任何一个模块继续下钻，为什么这么设计、备选方案是什么、为什么放弃、实现时踩了什么坑，我能一路讲到取舍和细节级；只背过材料的人到第二层就断了。第二个手段是仓库本身：项目是公开的，提交历史的时间线、每一轮评审的发现与修复记录、决策文档、测试代码全部可查，口头叙事和提交历史能不能对上，一看便知。第三个是我主动提供的：「我一开始理解错了、后来修正」的问题清单我是留着的——比如我以为某层失败不写栅栏记录是实现遗漏，后来才理解那是刻意的语义设计。能讲清自己曾经的误解，恰是真做过的人特有的材料。
- 追问2「为什么不用现成的编排框架，比如 LangGraph 那类？」口播：我不回避这个问题——生态里确实有现成的方案，我没有填补空白的野心，这个项目的价值定位是诚实的：它是我的个人简历项目，目标是展示后端工程深度，不是做一个有用户的产品。理由是：并发模型怎么设计、崩溃恢复怎么防重复花钱、容错怎么分层、可观测怎么埋点、分布式解耦怎么做——这些面试官真正想考的后端能力，只有从 0 做过一遍才真正拥有；如果基于现成框架搭，我最终学到的是那个框架的配置和 API，而不是这些机制为什么这么设计、代价是什么。所以从 0 复现是我的手段，我甚至在设计文档里写了与现成方案的对比和这个定位的诚实声明。换句话说：我不是不知道轮子存在，我是刻意通过造轮子来获得轮子的知识——并且我知道这在生产环境是不成立的，生产里当然用现成的。

**G2（主问）「这个项目有哪些没做或做得不够的地方？」**

口播：我主动列四条边界，每条都说清现状和补法。第一，崩溃恢复没有生产侧的自动触发：恢复协议本身正确、有完整的测试和真库验证，但「进程崩了谁来发现、谁来调恢复」这层部署侧编排没做，目前调用方都是测试代码。第二，消息队列解耦目前是单进程语义：生产者和消费者在同一个应用里，跨节点部署没做，发送侧也没有事务性发件箱，发送失败会留下悬空的待执行记录。第三，加密密钥没有轮换机制，换密钥后存量密文解不开，目前靠消费端单行容错兜底。第四，没有系统级压测：我有单元级的并发正确性断言、有真实环境的端到端功能验证，但没有吞吐和延迟数字，所以我在任何场合都不引用性能数据。我认为主动知道边界、说清每一项的补法，比假装完备可信得多——面试考察的也包括你对自己系统局限的认知。

- 追问1「如果给你时间，最先补哪个？」口播：我会最先补恢复的生产触发。排序理由是它是唯一挡在「能力可用」和「能力可运营」之间的——恢复协议已经实现了、验证了，只差一个触发者，补上它整个容错闭环才算在生产意义上成立；补法也想好了：消费端认领执行权时检测到残留的执行中状态就先走恢复流程，复用现有协议，改动面小。消息队列跨节点和密钥轮换其次，它们是有明确路径的增量；压测最后，因为它需要真实流量模型才有意义，个人项目造一个假的压测场景意义不大。

### 主题 H：扩展追问（覆盖剩余高频题）

**H1（主问）「出了问题你怎么排查？可观测性做了什么？」**

口播：我的可观测是「查得清 + 看得见 + 算得准」三层。查得清：每次工作流执行都有结构化的执行轨迹，按引擎的分层结构组织——每个节点记下结果、耗时、重试情况，崩溃了或者跑错了，把轨迹调出来就能定位到具体哪层哪个节点、失败原因是什么；轨迹接口按所有权校验访问。看得见：接入了标准的指标体系，暴露了几族核心指标——工作流执行数按状态分布、节点耗时分位数、token 消耗、预估成本、预算超限——接监控面板做了六块看板，整套监控栈我在本机用容器实际部署验证过，五个容器健康、面板全有数据。算得准：成本按模型单价表换算，token 和花费都能按模型维度归因。排查的实战口径是：先看执行轨迹定位到节点级，再看指标看是普遍慢还是个别慢，成本异常就按模型归因。

- 追问1「分位数指标为什么要专门开直方图？」口播：因为普通的均值和计数器算不出分位数——监控系统里常见的百分位延迟需要直方图桶数据来聚合，我在耗时指标上显式开启了分位数直方图发布，监控端才能画出 p50、p95、p99。这里踩过一个具体的坑：面板照抄示例查询时状态标签的大小写写错了，和指标里实际的小写值不匹配，结果整块面板空白——教训是抄查询语句必须核对实际标签值，而不是想当然。
- 追问2「成本怎么算的？」口播：按「token 用量乘模型单价」核算：每个节点执行后记录输入输出的 token 用量，乘以对应模型的单价得到预估成本；单价表是启动期加载的配置文件，新模型上线加一份价格配置就行，不用改代码。成本数据有两个出口：进指标体系，在面板上看趋势和按模型归因；进执行轨迹，能查到单次执行每一笔。在此基础上还有一道预算防线：工作流可以在声明里带上预算上限，运行中每一轮都累计、超阈值触发一次告警——注意是告警不是中止，硬拦截由提交守卫在事前负责，这是我自己拍板的分工：两层不重复设卡，事前防失控提交，事中给可见性。这里我修过一个低估成本的真实缺陷，教训是每一轮都要记账、包括失败的轮次。

**H2（主问）「用户怎么描述一个工作流？DSL 怎么设计的，怎么防止用户写错？」**

口播：用户用 YAML 声明工作流：整体是一份配置，里面有节点列表——每个节点声明用什么 Agent、提示词模板、输出通道——和元信息，比如模型偏好、预算上限。设计上我有意让它「声明式 + 可校验」：用户只描述「要什么」，不写控制流代码，并发、重试、恢复全部是引擎的职责，用户写不出来错。防写错靠三层校验：第一层是结构层，反序列化时字段类型、枚举值不合法直接报错，配合 JSON Schema 编辑器还能在 IDE 里获得提示和补全；第二层是语义层，校验引用关系——提示词里引用的通道存不存在、声明的工具有没有权限用、参数是不是负数这种业务约束；第三层是拓扑层，对节点图做完整性检查——有没有环、有没有孤儿节点，有环直接拒绝，因为我的执行模型建立在可分层的前提上。三层校验在解析期全部完成，错误都拦截在执行之前，不会出现跑了一半才发现配置非法的情况。

- 追问1「提示词模板怎么实现的？有没有注入风险？」口播：模板用表达式做占位替换，语法上引用上游输出和工作流入参。安全上我做了刻意的收窄：表达式求值用受限上下文——只注册了属性访问能力，类型定位、方法调用这些能力全部禁掉，所以用户在模板里写不了任意表达式、调不了任意方法，最坏也就是替换不出来，不会变成代码执行。这个收窄是从安全评审里固化下来的：模板是用户输入，按不可信输入对待。
- 追问2「校验报错对用户友好吗？」口播：我按「一次报出所有错、指到具体位置」的方向做的。结构错误报字段路径和期望类型，比如「第三个节点的超时字段应为正整数」；语义错误报具体引用了什么不存在的名字，比如「节点 A 的提示词引用了不存在的通道 X」——用户不用翻文档猜命名；拓扑错误报环的具体节点路径而不是只说有环。三类错误合并成一次校验结果返回，用户改一轮就能修完所有问题，而不是改一个错一个。另外开发期还有干跑模式：不调模型、零成本把拓扑和模板完整走一遍，提前验证配置——联调时先干跑再提交真实执行，省钱也省时间。错误信息的质量是我刻意的投入，因为 DSL 的用户体验一半在报错。

**H3（主问）「工作流定义改了，正在跑的实例怎么办？」**

口播：这是生产级编排必须回答的版本一致性问题。我的方案是定义快照化：每次提交，把那份解析后的定义按「名称加版本」存进数据库，执行实例绑定这个版本；用户后来改了定义、版本号升上去，在途的旧实例仍然按它当初绑定的旧定义跑到终态——恢复、重试也从库里取旧定义，不从代码或文件系统里读。也就是说版本升级只影响新提交，不波及在途执行，避免了「跑一半拓扑变了」这种无法恢复的混乱。同时做了冲突检测：实例执行到的版本和当前最新版本不一致时，接口能报出来，但只是警告不阻断——在途实例稳定跑完优先，这是我的取舍：宁可让用户看到一条「你有个旧版本实例还在跑」的提示，也不把正在跑的东西中断掉。

- 追问1「为什么存定义快照而不是每次从文件读？」口播：两个原因，都关乎正确性。第一是执行一致性：从文件或代码里读定义，文件一改就会波及在途实例——用户上午提交、下午改了文件，上午那个实例跑到一半发现自己按新拓扑执行了，这是不可接受的；快照化把「用户想改的定义」和「实例在用的定义」解耦成两份独立事实，实例绑定快照后用户随便改。第二是恢复依赖它：崩溃恢复要按实例当初的定义重建拓扑图，如果定义本身可能已经变过，恢复出来的图可能和崩溃前正在执行的图对不上——已完成的节点对不上位置、路由判断失去前提。快照保证恢复永远拿到和崩溃当时一模一样的定义，恢复的正确性建立在定义不可变之上。这两个理由归根到底是一句话：定义是执行和恢复的共同前提，前提必须冻结。
- 追问2「版本冲突为什么只警告不阻断？」口播：这是权衡后的取舍。在途实例是被它绑定的定义快照保护着的——它按旧版本执行的结果是完全确定的、正确的，没有任何受损；这时如果因为「存在新版本」就把它阻断或中断，反而制造问题：用户并没有合理的手段去中断一个正在正确执行的任务，强行打断只会浪费已产生的执行成本。所以我选择警告不阻断——接口把「这个实例跑的是旧版本、当前已有新版本」暴露出来，运维能看到、能决策，但系统不替用户做破坏性的决定。这背后是我对版本管理最重要的一条判断：要分清「需要一致的读」和「需要最新的读」——执行和恢复需要一致（绑快照），运维观察需要最新（报冲突），两类读分开服务，就不需要用「阻断」这种一刀切的手段。

**H4（主问）「开发的时候 LLM 调用成本怎么控制的？」**

口播：核心手段是一个零成本的模拟模式：绝大多数开发迭代跑在模拟后端上——每个节点从工作流配置里读预设的响应，支持引用上游输出的占位符，语义上和真实调用等价（同样的编排、同样的数据流、同样的恢复语义），但一分钱 LLM 调用都没有。这带来三个直接收益：每轮持续集成都能全绿，不存在因为额度或网络抖动导致的假失败；迭代速度快，不需要等真实模型的响应延迟；测试可以精确断言——预设响应是确定的，断言可以写到值级别。真实模型只在两个场景启用：端到端验证用真实密钥跑通从接口到模型的全链路，断言真实输出非空、真实计费进指标；以及演示时。真实模式的装配我做了严格门控：显式配置开关加密钥存在才启用，密钥只从环境变量读；真实模式下如果密钥缺失，启动直接失败——绝不静默回落到模拟模式假装真实，那是我定义过的「假成功」，会让人误以为验证过实际没有。

- 追问1「mock 模式会不会和真实行为不一致，测了个寂寞？」口播：会有边界，我分两层回答。编排语义层——分层、合并、恢复、重试——模拟模式与真实完全一致，因为引擎对两者一视同仁，Agent 只是可替换的实现；这层在模拟下测是充分的。模型行为层——真实模型的输出内容、异常类型、超时分布——模拟模式代表不了，所以我把它交给真实密钥门控的端到端测试：有密钥就真跑并断言真实输出与计费，没有密钥自动跳过、构建不红。风险敞口就是「本地没配密钥、只跑过模拟」的情况，我靠持续集成里的真实调用记录兜底，并主动承认这是分层测试的边界而不是全覆盖。
- 追问2「成本超了怎么办？有没有防失控的手段？」口播：两道防线。事前是提交守卫：提交时就校验节点数上限和按模板长度估算的预估成本，超了直接拒绝——防的是恶意或失控的配置还没执行就拦下；事后是预算告警：工作流声明预算上限，运行中逐轮累计，超阈值触发一次告警。这里有个我修过的真缺陷：最初记账只记成功路径的最后一次调用，中间轮次全漏，实测低估最多三倍——改成逐轮记账后才真实。两个防线分工明确：守卫是硬拦截，预算是记账告警不阻断，不重复设卡。

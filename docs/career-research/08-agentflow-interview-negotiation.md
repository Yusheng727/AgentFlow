## 一、BSP 执行引擎（两版都有 · 必考之首）

**简历原话**：A 版「BSP（整体同步并行）执行引擎……Virtual Threads 层内并行 + barrier 确定性合并（免锁并发）」；B 版「同层节点 Virtual Threads 并行 + CompletableFuture.allOf 层间 barrier；只读快照保证层内互不可见，声明序 Reducer 解决并发写冲突（免锁设计）」。

### 【30 秒人话版】（背这个）
> BSP 是一种并行计算模型：把执行分成一轮轮"超步"（superstep），每轮内所有节点各跑各的、互不通信，轮末有一个 barrier（栅栏）——所有节点都干完才合并结果进下一轮。我在 AgentFlow 里把 YAML 声明的工作流 DAG 按"最长路径"预分层，每层就是一个超步：层内用 Java 21 虚拟线程并行执行，`CompletableFuture.allOf` 做栅栏，栅栏过后按声明序合并各节点输出。好处是并发模型极其简单——层内节点互相看不见对方，根本不存在数据竞争，所以不需要锁。

### 面试官问法 × 答法

**Q1「为什么用 BSP，不用 Actor 模型或消息队列管并发？」**
> 因为工作流是**有界 DAG**——节点数有限、层数有限，不是无限流。这种场景下 barrier 换来的是"语义确定可测"：每层结束状态唯一、断言好写。消息队列管并发适合无界流式场景，用在这里是把简单问题复杂化。代价我也清楚：并行度受层内节点数限制，层的长短取决于 DAG 最长路径——但对几十个节点的工作流编排，这是正确的取舍。

**Q2「barrier 具体怎么实现的？」**
> 一句话：`CompletableFuture.allOf(这一层所有节点的 future)`，全部完成后才继续。配合虚拟线程（Java 21），每个节点一个 VT，阻塞时自动让出底层平台线程，几十个节点的并行开销可忽略。

**Q3「免锁并发具体指什么？」**
> 两个机制：① 只读快照——每层开始时对上下文做不可变快照，层内节点读的是快照，互相看不见对方的写入，竞态从根上不存在；② 声明序 Reducer——多个节点往同一个 channel 写时，按 YAML 里的声明顺序合并（不是按完成时序），保证结果确定性。

**Q4（A 版）「动态路由怎么在 BSP 下工作？路由了不就破坏同步模型了吗？」**（你的简历 lead 里这句就是钩子）
> 不破坏。静态图仍然预分层，但每层只跑"可达"的节点：运行时求值 `when` 谓词（SpEL）决定走哪条边，被路由切断的下游标 SKIPPED。循环同理——回边豁免分层，引擎用"双 active 集合 + 迭代轮次"表达有界循环，barrier 语义不变。**核心代价是动态路由牺牲了执行路径的确定性，我用 checkpoint 只持久化"已走的边"，恢复期从源节点 BFS 重算可达集，把确定性买回来。**（这句是 A 版「路由决策落 checkpoint 供恢复重放」的完整展开，务必背熟）

**Q5「最长路径分层是什么？」**
> 拓扑排序之后，每个节点的层数 = 上游最大层数 + 1（关键路径思想）。算出来的层号就是超步编号，同一层的节点没有任何依赖，可以安全并行。

## 二、Checkpoint 与崩溃恢复（两版都有 · 必考第二）

**简历原话**：A 版 lead「两级 Checkpoint 崩溃恢复」+「节点级完成即持久化输出防 LLM 重复计费 + 路由决策 BFS 重放恢复」。

### 【30 秒人话版】（背这个）
> Checkpoint 就是游戏存档。我的系统有两级：**节点级**——每个节点一跑完立刻把输出写进 PostgreSQL，因为节点背后是真实的 LLM 调用，是真金白银，崩了恢复时已完成的节点直接重放结果、绝不能重跑，这就是简历里"防 LLM 重复计费"的含义；**层级（barrier 级）**——每层栅栏处写快照，标记"这一层整体完成了"。恢复协议先查崩溃发生在哪一层，只重跑该层未完成的节点，之前的层全部重放。

### 面试官问法 × 答法

**Q1「为什么要两级，一级不行吗？」**
> 职责不同：节点级保**钱**（已完成节点的 LLM 花费不可重复），层级保**一致性**（"哪些层已整体完成"是恢复的定位锚点）。只有节点级，恢复时无法快速定位"崩在哪"；只有层级，粒度太粗，半层的已完成节点会被重跑、重复计费。

**Q2「恢复时怎么知道从哪恢复？」——这里有一个你的 P0 踩坑故事，主动讲**
> 这里我修过一个评审抓出来的 off-by-one 正确性 bug：最初的恢复协议查的是"已完成的层"，实际应该查"崩溃层本身"（nextSuperStep 语义）——查错了层会导致崩溃层的已完成节点被跳过或重跑。另外还有一个 stray COMPLETED 防护：超时 abort 后，还在飞的任务可能事后把 COMPLETED 写进库里，恢复时要按工作流状态鉴别，宁可该层整体重跑（重复计费是软约束），也不能用没过 barrier 的脏数据（正确性是硬约束）。这两个都是多视角代码评审发现、4 个独立视角确认的 P0。

**Q3「谁触发恢复？」——已知边界，如实答（账本 claim-agentflow-003明确要求）**
> 如实说：`recoverAndExecute` 的生产入口（崩溃检测→自动调恢复的调度器）没做，目前所有调用方是测试。个人项目做到"恢复协议本身正确且有真 PG 集成测试验证"，调度编排属于部署侧，这是我明确的已知边界。**主动说边界比被戳穿强得多。**

**Q4（B 版）「真 PostgreSQL 验证验证了什么？」**
> 真 PG 集成测试实跑：Flyway 迁移、checkpoint 往返、加密密文证据。而且真 PG 暴露了两个 mock/H2 环境永远发现不了的 bug——持久化卷导致测试间数据残留互渗、毫秒级时间戳碰撞导致排序不稳定。这是"测试环境 vs 生产环境"差异的活例子。

## 三、HITL 人工审批（A 版重点 · Agent 岗 JD 逐字命中）

**简历原话**：A 版「HITL 人工审批全链路（任务中断 / 敏感操作确认 / 审批后恢复）：上下文快照随审批单落库（只含兄弟输出防恢复双跑），REST/Web UI 决策后重跑待批节点续跑下游；decidedBy 服务端推导防审计身份伪造，多级审批链可再次暂停」。

### 【30 秒人话版】（背这个）
> HITL = Human-in-the-Loop，人工在环：工作流跑到敏感节点（比如要动钱的操作）时暂停，等人工审批后再继续。我的全链路五步：① 节点抛出"需要审批"信号 → ② 引擎暂停工作流，把当前上下文快照连同审批单写库，状态置为 AWAITING_APPROVAL → ③ 审批人通过 REST 或 Web UI 审批中心做 APPROVE/REJECT → ④ 批准则重建上下文、只重跑待批的那个节点 → ⑤ 从审批层继续往下跑完。B 版简历虽然没展开 HITL，但「崩溃 / 审批 / 循环三条恢复路径共用同一套重放续跑骨架」里的"审批"就是它——被问到要能接上。

### 面试官问法 × 答法

**Q1「快照为什么只含兄弟节点输出？」**（设计亮点，主动讲）
> 恢复时兄弟节点不该重跑——它们已经执行过、LLM 钱已经花了。所以暂停时只把同层其他节点的输出存进审批单快照，待批节点自己不在快照里，恢复时单独重跑它。这是"防 LLM 重复计费"在 HITL 场景的镜像。

**Q2「decidedBy 防伪造是什么意思？」**
> 审批记录里"是谁批的"由服务端从鉴权身份推导，不由请求体传入——否则任何人可以伪造"总经理批准了"。配套还有决策原子幂等：两个并发请求同时批同一单，只有一个生效。

**Q3「REJECT 之后呢？」**
> 工作流直接置 FAILED 终态，不重跑。

**Q4「审批人是谁？」——边界如实答**
> 审批人模型 = 创建者 ∪ admin，没有独立的审批角色和会签。个人项目的已知边界，业务扩展时再加。

## 四、Kafka 异步解耦与幂等（B 版重点 · 后端必考）

**简历原话**：B 版「提交 / 执行经 Kafka 解耦；消费端单条条件 UPDATE 原子认领执行权，at-least-once 投递下防重复消费双跑双计费」+「提交守卫事前拦截失控 DAG（节点数 / 预估成本 422）+ per-workflow 预算逐轮记账与阈值告警两道防线」。

### 【30 秒人话版】（背这个）
> 用户提交工作流后，API 只往 Kafka 发一条消息就返回 202，真正的执行由消费者异步做——这就是提交/执行解耦：API 不被长任务拖住，消费者挂了消息还在、可重投。但 Kafka 是 at-least-once 语义——消息保证至少送到一次、可能重复送，所以消费端必须幂等。我的手段：消费者用一条 `UPDATE ... WHERE status='PENDING'` 的**单条条件更新**原子认领执行权，状态从 PENDING 变 RUNNING，两个消费者抢同一条消息只有一个能改成功，另一个影响行数为零就放弃——重复投递不会导致重复执行、重复计费。

### 面试官问法 × 答法

**Q1「at-least-once 是什么？」**
> 消息系统的投递保证分三档：at-most-once（可能丢）、at-least-once（可能重）、exactly-once（代价高且多限于 Kafka 内部事务）。跨系统的业务幂等通常自己做——我就是在消费端用状态机的条件转移做的，不是依赖什么消费注解。

**Q2「条件 UPDATE 为什么能防并发？」**
> 数据库单条 UPDATE 带 WHERE 条件是原子的：两个事务同时执行 `UPDATE ... SET status='RUNNING' WHERE id=? AND status='PENDING'`，数据库行锁保证串行，第一个成功改了状态，第二个的 WHERE 匹配不到行、影响行数 0，放弃执行。这比"先查后改"（check-then-act）的写法强——后者在两步之间有竞态窗口。

**Q3「auto.offset.reset 为什么是 earliest？」**
> 任务队列语义：新消费组订阅时应该能拿到订阅前生产的消息（不丢任务），所以 earliest 而不是 latest。正因为消费端幂等，重扫旧消息是安全的。

**Q4「retry 被幂等吞掉的真 bug」——必讲的故事（简历没直接写，但这是你最好的"测试绿≠生产生效"素材）**
> 我的重试（retry）消息一开始被消费者"终态跳过"的幂等防护误吞了——终态跳过本来是防重复消费的，但 retry 恰恰是要重新执行已终态的工作流，结果被静默跳过，重试永远不生效。本地单测全绿，只有真 Kafka E2E 才暴露。修法：retry 先把状态复位为 PENDING 再派发。这个故事有三个教训：幂等防护要区分"重复的正常消息"和"刻意的重试消息"；集成测试要覆盖真实中间件语义；测试绿≠生产生效。

**Q5「两道防线是什么分工？」**
> 提交守卫是**事前硬拦截**：提交时校验节点数上限、按 token 单价预估成本，超了直接 422 拒绝——防恶意或失控的 DAG 起无界线程烧钱。per-workflow 预算是**事后记账告警**：运行中逐轮累计，超阈值触发一次告警（edge-triggered，不重复触发）。拍板过的分工：预算是记账/告警非阻断，硬防护归提交守卫，两层不重复设卡。

**Q6「预算逐轮记账为什么值得写？」——踩坑故事二**
> 最初的记账只记"成功路径的最后一次调用"，schema 校验重试、工具多轮循环这些中间轮次的 token 全漏了——实测低估最多 3 倍。评审抓到后改成逐轮记账。LLM 成本估不准的根源通常就是"只算最后一轮"。

**Q7（边界）「现在是分布式吗？」**
> 如实答：当前是单 JVM 语义——生产者和消费者在同一个应用里，Kafka 解耦的是提交/执行的模块边界，不是跨节点部署；send 是异步的、没做 outbox，发送失败会留悬空 PENDING，这是已知边界。但消费者幂等、条件认领这些语义是为多实例扩展预留的，加上就能水平扩展。

## 五、安全横切（两版都有）

**简历原话**：A 版「工具级授权（config ∪ DB）+ 5 列 AES-256-GCM 静态加密（生产 fail-closed）+ 提交守卫 422 硬拦截」；B 版「工具级授权（config ∪ DB、admin-only、防自授）+ 5 列 AES-256-GCM 静态加密（生产 fail-closed）+ API Key 只存 SHA-256 哈希防越权」。

### 【30 秒人话版】（背这个）
> 三件事：① **静态加密**——敏感数据落库（躺在磁盘上）时是密文。我用 AES-256-GCM，GCM 是带认证的加密模式，密文被篡改能被检测出来；密文带自描述前缀，老明文数据兼容可读。② **API Key 只存 SHA-256 哈希**——数据库被拖库也拿不到可用 key，验证时对提交的 key 现算哈希比对。③ **工具级授权**——每个调用者只能用被授权的工具，授权来自 config 与数据库两处求和，管理接口 admin-only，防止普通用户给自己授特权工具。

### 面试官问法 × 答法

**Q1「fail-closed 是什么？」**
> 生产环境启动时如果没配加密 key，系统**拒绝启动**而不是明文落库。fail-open（没 key 就明文）图省事但安全上等于没做。这是从配置层面把"忘记配 key"变成"起不来必须处理"。

**Q2「哪 5 列？为什么是这 5 列？」——扩列判据要背熟**
> 判据一句话：**列内是否含业务敏感数据**，不是拍脑袋凑数。5 处：节点输出（含 LLM 响应原文）、channel 数据、审批载荷（可能含金额）、路由决策（含业务上下文）、工作流定义里的 prompt 模板（业务话术）。被问"为什么不多加密几列"→ 加密有成本（性能、运维、key 轮换），按判据最小必要覆盖。

**Q3「SHA-256 哈希为什么不直接存 key？」**
> 哈希不可逆。存原文则拖库即泄密；存哈希则验证时对提交 key 现算哈希比对即可，库里永远没有可用凭证。配套还有所有权校验防 IDOR（用户 A 拿 ID 访问用户 B 的工作流会被拒绝）。

**Q4（边界）「key 轮换呢？」**
> 未实现——换 key 旧行不可解。聚合查询端点做了损坏行容错（单行解密失败跳过记 warn，不让整个列表 500）。如实说边界。

## 六、双框架适配器与 RAG（A 版 · Agent 岗）

**简历原话**：A 版「Spring AI 2.0 与 LangChain4j 收敛同一 AgentFunction 窄接口——core 零 LLM 框架依赖（构建级证明）+ RAG 扩展点引擎零改动；真实 DeepSeek 端到端（真实 token 落 Grafana）」。

### 【30 秒人话版】（背这个）
> LLM 框架（Spring AI、LangChain4j）API 各不相同，我把"调 LLM"这件事收敛到一个自定的窄接口 `AgentFunction` 后面：引擎只认这个接口，两个框架各写一个适配器实现它。**"core 零框架依赖"是构建级证明**——把任何一个适配器模块从构建里删掉，引擎照样编译通过，说明依赖方向真的干净。RAG（检索增强生成）也验证了扩展点：检索→增强→委托作为一个新的 AgentFunction 实现接入，引擎一行代码没改（有专门的零改动测试）。

### 面试官问法 × 答法

**Q1「RAG 是什么？」**
> Retrieval-Augmented Generation：先从知识库里检索相关片段，塞进 prompt 再让 LLM 回答——治幻觉、让模型用上私有数据。我的 RAG 是 demo 级（内存向量库 + 确定性 embedding，**有意的最小验证实现**，目的是证明扩展点成立，不是产品级检索），如实说定位。

**Q2「真实 DeepSeek 端到端验证了什么？」**
> 用真实 API key 跑通 REST→DSL→引擎→适配器→LLM 全链路，断言真实输出非空、真实 token 计费进了 Prometheus/Grafana。凭证只从环境变量读，缺 key 启动直接失败（fail-fast，绝不静默回落 mock 假装真实）。

**Q3「为什么不用现成的 LangGraph4j？」——档 C ① 必问题，30 秒答案**
> 这个项目从 0 复现的目的不是填补生态空白（现成库已经存在），而是展示后端工程深度：并发模型、崩溃恢复、容错、可观测、解耦这些能力，只有自己从 0 做过才真正拥有。选型时我明确对比过——见下一条总策略。
